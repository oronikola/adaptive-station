# IP-007 — SMS Gateway Fleet (Adaptive-Station-Owned)

**Date:** 2026-09-09
**Status:** Implemented
**Depends on:** IP-002 (tenant/station model). Extends the existing parent
notification workflow (`App\Jobs\DispatchParentTapNotification`,
`App\Events\TapRecorded`, FCM push) — that workflow predates this plan and
has no IP of its own; this document only adds the SMS channel to it.

## Objective

Give parents an SMS alert when their child taps IN/OUT at school, delivered
entirely through Adaptive-Station-owned infrastructure, at real scale (a
fleet of 15-40+ dual-SIM Android phones). Per the settled MVP decision in
[DATA_OWNERSHIP_AND_TENANT_MODEL.md](../milestone-0-foundation/DATA_OWNERSHIP_AND_TENANT_MODEL.md)
§"Notifications (SMS)": the legacy `tapbunker` SMS queue is archived, not
kept running, and Adaptive Station's own notification workflow is the single
delivery owner. This system **does not** write to or read from `tapbunker`
or any legacy/third-party SMS backend (e.g. `essentiel.ph`) — that would
violate the settled decision and IP-005's explicit constraint against legacy
SMS write support (enforced by a static grep test, see Verification).

An earlier draft of this plan assumed one device polling a statically
assigned set of schools — the same shape as `essentiel.ph`'s own setup,
which (per direct confirmation from that system's developer) is exactly why
it suffered severe delivery delays under load: a busy school's messages
queued up behind its one assigned device while other devices sat idle. This
implementation is architected instead as a **global, tenant-agnostic work
queue**: every SIM line is a fungible worker that claims from one shared
pool across every tenant, with atomic claiming (no double-sends across
concurrent pollers) and a lease timeout (no message stuck forever behind one
crashed phone).

The delivery mechanism reuses the existing `dual_sim_sms` Flutter/Kotlin app
(a separate repo) that sends via Android's native `SmsManager`. Its sending
engine (SIM round-robin, daily rate limit, foreground service) is reused
as-is; only the backend it polls, and the polling contract, change.

## What was built

- `sms_outbox` (central `mysql` connection) — the work queue. No tenant or
  station filter anywhere in the claim path; that omission is the entire
  fix for the essentiel.ph bottleneck.
- `sms_gateway_devices` + `sms_gateway_device_tokens` — the fleet roster and
  its bearer credentials, split the same way `Station`/`StationCredential`
  are, so revoking one lost/reset phone never touches the rest of the fleet.
- `AuthenticateSmsGatewayDevice` middleware + `SmsGatewayController`
  (`POST /api/v1/device/sms/claim`, `POST /api/v1/device/sms/messages/{id}/status`).
- `DispatchParentTapNotification` now also enqueues a `pending`
  `SmsOutboxMessage` per opted-in parent, alongside its existing broadcast +
  FCM push.
- `phone_number` on `parent_accounts`; `notify_sms` added to
  `notification_preferences` (default `false`, opt-in) via
  `NotificationPreferenceController`.
- Two scheduled commands (`routes/console.php`): `sms:reclaim-stale-claims`
  (every minute) and `sms:expire-stale-outbox` (every 5 minutes).
- Platform portal page (`platform.sms-gateway.devices.*`) — fleet roster
  with online/offline status and sent/failed-today counts, plus backlog
  metrics (pending, claimed, failed-24h, oldest-pending age).
- Feature tests: `SmsGatewayDeviceApiTest`, `SmsOutboxConcurrencyTest`,
  `ParentSmsNotificationTest`, `NoLegacySmsBackendContactTest`.

## Schema

**`sms_outbox`**: `id` (uuid), `tenant_id`, `person_id`, `parent_account_id`,
`station_id`, `tap_event_id` (plain uuid columns, no FK — same reasoning as
`StationActivationCode`'s `station_id`), `phone_number`, `message`, `status`
(`pending`/`claimed`/`sent`/`failed`/`expired`), `attempts`,
`claimed_by_device_id`, `claimed_at`, `expires_at` (set at insert time,
`now()+30min` — a very late "tapped in" alert is worse than none), `sent_at`,
`last_error`, `created_at`. Indexes: `(status, created_at)` for the claim
scan, `(status, claimed_at)` for the reclaim job, `(tenant_id, status)` for
the portal backlog metric.

**`sms_gateway_devices`**: `id`, `label`, `is_active`, `last_seen_at`,
`sent_today`, `failed_today`, `stats_date` (rolled over lazily on each claim
poll via `resetDailyStatsIfNeeded()`, avoiding a separate reset job).

**`sms_gateway_device_tokens`**: `id`, `device_id` (FK), `token_hash`
(sha256, unique), `last_used_at`, `revoked_at`, `created_at`.

**`parent_accounts`**: `+ phone_number` (nullable). `notification_preferences`
JSON gained the `notify_sms` key — `NotificationPreferenceController` now
merges (`array_merge(DEFAULTS, existing, incoming)`) rather than overwriting
wholesale, so an older app version that doesn't send `notify_sms` yet can't
silently wipe it.

## Claim/lifecycle design — and a real lesson learned building it

`SmsOutboxMessage::claimBatch(SmsGatewayDevice $device, int $batchSize)`
is the batch analogue of `StationActivationCode::redeem()`'s
`lockForUpdate()` pattern, using `->lock('for update skip locked')` (Laravel
has no `skipLocked()` helper — `->lock()` takes a raw lock-clause string).
Verified against the actual server: **MariaDB 11.8.2**, which has supported
`SKIP LOCKED` since 10.6.

Two design decisions came directly out of debugging a failing concurrency
test, and both matter for real production throughput, not just the test:

1. **The claim query filters on `status = 'pending'` alone** — it does
   *not* also inline-reclaim lease-expired `claimed` rows in the same query
   (an earlier draft did). An `OR` across two status branches can't be
   satisfied by a single ordered index range scan, which forces MariaDB
   into a filesort — and a filesort under `FOR UPDATE` locks *every row it
   reads to sort*, not just the ones the `LIMIT` keeps. That lets one
   device's claim transaction lock the entire candidate pool and starve
   every concurrent poller, exactly the failure mode this design exists to
   avoid. The scheduled `sms:reclaim-stale-claims` command (every minute)
   is the sole path back to `pending` for an abandoned claim; a ~1 minute
   worst case is a good trade for keeping the hot path index-ordered.
2. **Claimed rows are updated one at a time by primary key**
   (`$row->forceFill([...])->save()` in a loop), not via a single bulk
   `UPDATE ... WHERE id IN (...)`. A multi-value `IN` list isn't guaranteed
   to be served via the primary key — on a low-cardinality table MariaDB
   can instead scan a secondary index, locking every row it scans to
   evaluate the filter. A plain `WHERE id = ?` is always index-served
   regardless of table size, and every row here is already X-locked by the
   same transaction from the `SELECT` above, so this never waits.

Both were caught and fixed via `EXPLAIN` during test development (see
`SmsOutboxConcurrencyTest`) — worth remembering if this query is ever
touched again: re-verify with `EXPLAIN` that no `Using filesort` appears and
that update statements resolve via `PRIMARY`.

**Retry policy**: a `failed` report (`SmsOutboxMessage::markFailed()`) puts
the row back to `pending` while `attempts < MAX_ATTEMPTS` (3), then
dead-letters to `failed` permanently. `SmsGatewayController::reportStatus()`
scopes its lookup to `claimed_by_device_id = $device->id`, so a device can
never report status on a row it didn't claim.

## Security Constraints

- SMS device tokens are a distinct credential type, scoped only to the two
  `sms/*` endpoints — never able to read parent/student PII beyond the
  phone number and message text already destined for that phone.
- Device identity (`SmsGatewayDevice`) and secret (`SmsGatewayDeviceToken`)
  are split — losing one phone means revoking exactly one token with zero
  effect on the rest of the fleet.
- Revocation is checked on every request via
  `SmsGatewayDeviceToken::findActiveByPlaintextToken()`'s
  `whereNull('revoked_at')`.
- No SIM/device is tenant-pinned in code or schema — enforced as a design
  invariant with a code comment on `claimBatch()`; a future change that adds
  a tenant filter there would silently reintroduce the essentiel.ph bug.
- Never write to `tapbunker` or call any `essentiel.ph` endpoint —
  `NoLegacySmsBackendContactTest` statically greps `app/` (with comments
  stripped, so documentation of this constraint doesn't trip its own check)
  for either name.

## Device-app contract (separate `dual_sim_sms` repo — not built here)

- Bearer token per physical phone (not per-school), issued via the
  platform portal.
- Poll `POST /api/v1/device/sms/claim` every ~15-20s with a modest batch
  size (10-20 — the endpoint defaults to 20, caps at 50).
- Report status immediately after each individual send via
  `POST /api/v1/device/sms/messages/{id}/status`, not batched at the end —
  this is what makes the reclaim lease and live fleet stats meaningful.
- Per-SIM send pacing should become server-configurable rather than the
  app's current hardcoded 10-second delay — deferred; not built in this
  pass.

## Verification / Exit Criteria

All verified by the automated test suite (`php artisan test`, 202 passing):

- **No double-claim under concurrency** (`SmsOutboxConcurrencyTest`) — a
  genuinely separate second database connection holds `FOR UPDATE` locks on
  10 of 20 seeded rows; `claimBatch()` on the primary connection returns
  exactly the other 10, with zero overlap.
- **Reclaim after timeout** — a `claimed` row 10 minutes stale is released
  by `sms:reclaim-stale-claims --minutes=5` and becomes claimable again.
- **Expiry** — a `pending` row past `expires_at` is marked `expired` by
  `sms:expire-stale-outbox` and excluded from claiming.
- **Retry-then-dead-letter** — three `failed` reports on one row: `pending`
  after attempts 1-2, `failed` (no longer claimable) after attempt 3.
- **Tap-to-outbox** (`ParentSmsNotificationTest`) — a tap for a
  `notify_sms`-enabled parent with a phone number produces exactly one
  `pending` row; disabled preference, missing phone number, or a muted
  IN/OUT direction each produce zero rows.
- **Auth boundary** — missing/revoked/deactivated-device tokens rejected
  with 401/403; a device cannot report status on a row it didn't claim
  (404).
- **No legacy contact** (`NoLegacySmsBackendContactTest`) — static check,
  comments stripped, across all of `app/`.
- **Manual end-to-end** (not yet run — requires the repointed `dual_sim_sms`
  app): a real tap on a pilot station should result in an SMS arriving via
  a gateway phone.

# IP-002 — Milestone 1: Laravel Multi-Tenant Foundation

**Date:** 2026-09-02  
**Status:** Planned  
**Depends on:** IP-001

## Objective

Build the secure Adaptive Station cloud foundation: tenant-aware Laravel application, central MySQL schema, portal authentication, roles, stations, and auditability.

## Deliverables

- Laravel application with MySQL migrations based on the database-design document.
- Inertia/React/Tailwind portal shell.
- Platform-super-admin and tenant-admin authorization.
- Tenant, user, station, activation-code, and credential management.
- Automated tenant-isolation tests.

## Work Plan

1. Create Laravel project configuration for MySQL, queues, mail/logging, and environment-specific secrets.
2. Add migrations and models for `tenants`, `users`, `stations`, `station_credentials`, `station_activation_codes`, and `audit_logs`.
3. Implement roles and authorization policies: `platform_super_admin`, `tenant_admin`, and `tenant_operator`.
4. Add tenant query scopes and service helpers; require tenant context for tenant-owned resources.
5. Build the platform portal: tenant list/create/edit/suspend, tenant-admin invitation or creation, and audit views.
6. Build the school portal: school profile, administrator management, station list, station status, and activation-code generation.
7. Hash all device tokens and activation codes; make activation codes single-use and short-lived.
8. Log provisioning, role changes, activation-code creation, station disablement, and credential revocation.
9. Add feature tests for authorization and cross-tenant access denial; add database constraint/index tests.

## Data / API Boundaries

- Portal users are authenticated through Laravel.
- Platform users have no tenant ID; tenant users must have exactly one tenant ID for MVP.
- Stations are created under one tenant only and cannot be reassigned without an audited support operation.

## Verification / Exit Criteria

- Platform admin can provision a tenant, tenant admin, and pending station.
- Tenant admin sees and edits only its own tenant data.
- Activation codes and device secrets are never returned after initial creation.
- Cross-tenant route, model-binding, and API access tests fail closed.

## Risks

- A missed tenant filter can leak data; mitigate with central query scopes, policies, and negative authorization tests.

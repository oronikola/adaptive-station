# IP-001 — Milestone 0: Product and Migration Foundation

**Date:** 2026-09-02  
**Status:** Planned  
**Depends on:** None

## Objective

Establish the decisions, source-data inventory, pilot-school mapping, and operational safeguards needed to build Adaptive Station alongside the existing live tapping system without disrupting schools.

## Deliverables

- Approved MVP scope, data-ownership matrix, and tenant model.
- Field-level mapping from legacy sources to Adaptive Station entities.
- Pilot-school onboarding and migration checklist.
- Documented acceptance scenarios and reconciliation rules.
- Development, staging, and production environment baseline.

## Work Plan

1. Inspect the current WPF application, local SQLite schema, and remote MySQL access code.
2. Inventory all legacy dependencies: `studinfo`, `teacher`, `gradelevel`, `taphistory`, `tapbunker`, RFID aliases, kiosk `local.db`, and SMS behaviour.
3. Confirm product decisions: tenant identity, timezone policy, default one-minute duplicate window, IN/OUT semantics, card UID normalization, and notification ownership.
4. Define source-of-truth ownership for profiles, RFID assignments, tap events, notifications, and legacy exports.
5. Select one pilot school and collect sanitized schema/data samples plus its existing report requirements.
6. Produce mapping specifications for people, cards, attendance, stations, and source IDs.
7. Define import reconciliation: source count, imported count, known/skipped count, rejected count, ambiguous count, and final sign-off.
8. Set up repository conventions, environment variables, CI checks, error logging, backups, and secret-handling rules.
9. Confirm rollout method: parallel validation, station-by-station cutover, and rollback to legacy flow.

## Key Decisions Required

- Which system owns RFID-card assignment for the pilot school after cutover?
- Is legacy attendance export required during the pilot, and what field mapping does it need?
- Does the pilot require the existing SMS queue to continue operating?
- What historical attendance period must be imported?

## Verification / Exit Criteria

- Mapping document covers every required legacy field and identifies unmapped fields.
- Pilot migration checklist and rollback plan are reviewed by product and school stakeholders.
- No kiosk receives a cloud MySQL credential in the target design.
- MVP acceptance scenarios are approved and testable.

## Risks

- Legacy schemas vary across schools; mitigate with a connector mapping layer and pilot-specific driver.
- Existing `local.db` records may overlap with `taphistory`; mitigate with source IDs and reconciliation rules.

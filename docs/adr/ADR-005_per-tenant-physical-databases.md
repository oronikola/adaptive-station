# ADR-005 — Per-Tenant Physical Databases

**Date:** 2026-09-04
**Status:** Accepted
**Supersedes:** [ADR-001](ADR-001_shared-database-tenant-model.md)

## Context

ADR-001 chose one shared MySQL database with logical tenant isolation (`tenant_id` column + `TenantScope`) for the MVP, explicitly deferring per-tenant databases "post-MVP for enterprise customers who require it." The product direction changed: every school now gets its own physical MySQL database, matching how the operator runs other systems.

## Decision

Each tenant's data lives in its own database, named `adaptive_station_{code}` (e.g. `adaptive_station_cnhs`), created and migrated automatically when the tenant is provisioned (`Tenant::provision()`). A small set of central tables — `tenants`, `users`, `station_credentials`, `station_activation_codes`, `audit_logs` — stay in one shared database, because they are exactly what's needed to identify *which* tenant a request belongs to before a tenant-specific database connection can even be chosen (portal login resolves a `User` centrally; a kiosk's device token resolves a `StationCredential` centrally). Everything else — `stations`, `people`, `rfid_cards`, `tap_events`, `master_data_changes`, `device_heartbeats`, `device_sync_cursors`, `integration_profiles`, `integration_runs`, `import_batches`, `import_exceptions` — lives per-tenant.

**The existing `tenant_id` column and `TenantScope` global scope are kept on every tenant-owned table, not removed.** This is deliberate: ripping out the application-layer scoping to "rely solely on physical separation" would have multiplied the size of this change (touching every model, policy, and the full existing test suite) for no additional isolation benefit — a `tenant_id` column inside a database that only ever holds one tenant's rows costs nothing and is a free defense-in-depth layer. Physical separation is the *primary* isolation boundary now; `TenantScope` is the secondary one.

A new `App\Support\TenantDatabase` class is the single choke point for "which physical database does this tenant's data live in right now" — it dynamically repoints a `tenant` Laravel database connection at the correct `adaptive_station_{code}` database. Every tenant-owned Eloquent model declares `protected $connection = 'tenant';`; every central model (`Tenant`, `User`, `StationCredential`, `StationActivationCode`, `AuditLog`) explicitly declares `protected $connection = 'mysql';` — the latter is required, not cosmetic: Eloquent's `belongsTo()` silently makes a related model inherit the *caller's* connection when the related model has no connection of its own, which would otherwise point central-table lookups (like `Station::tenant()`) at the wrong database.

## Consequences

- **Tenant provisioning is slower and can fail differently.** Creating a tenant now means `CREATE DATABASE` + running 11 migrations, synchronously, in the same request (`Tenant::provision()`). A failure mid-provisioning rolls back the tenant row and drops any partially-created database — a tenant record is never left pointing at a missing/broken database.
- **Tenant deletion is simpler for the tenant-owned data** (`DROP DATABASE` replaces what used to be ~11 careful per-table deletes in foreign-key order) but the row-level deletes are *kept* too (see `Tenant::purge()`), because `DROP DATABASE` alone isn't provable/testable without a real per-tenant database in every test run — row-level deletes work identically whether or not physical separation is in play.
- **No single query spans multiple tenants' data anymore.** Platform-level cross-tenant views (station counts across all schools, the platform station list) now loop every tenant's database and merge in PHP. Fine at MVP scale; would need a denormalized cross-tenant index to scale further.
- **Two tables needed a schema change specifically because of this split**: `station_credentials` and `station_activation_codes` previously resolved their tenant via `whereHas('station', ...)` — impossible once `stations` moves to a different database — so both gained their own `tenant_id` column (`2026_09_03_020000_add_tenant_id_to_station_auth_tables.php`).
- **Two foreign keys became cross-database and had to be dropped**, not just omitted from new installs: `station_credentials.station_id` and `station_activation_codes.station_id` used to FK to the central `stations` table; already-migrated databases needed a follow-up migration (`2026_09_03_020001_drop_stations_fk_from_station_auth_tables.php`) to actually remove the constraint, since editing a migration file doesn't retroactively alter an already-applied schema.
- **A cross-database operation can't be one atomic transaction.** Device activation (central: activation code + new credential + audit log; tenant: the station row itself) is documented as two separate transactions, not one — a crash between them is a known, rare, recoverable-by-reissuing-a-code edge case, not silently ignored.
- **Testing uses one shared fixed physical database for the `tenant` connection for the whole suite**, not a real database per test tenant (see `tests/bootstrap.php`, `TenantDatabase::skipInTesting()`) — this is what makes keeping `TenantScope` worthwhile: different test tenants' rows coexist safely in that one database exactly as they did before this change, so the existing test suite needed no rewrite. A small number of dedicated tests (`TenantDatabaseProvisioningTest`, `TenantDatabaseDeletionTest`, `BackfillTenantDatabasesCommandTest`) use an explicit escape hatch (`TenantDatabase::$forceRealDatabaseOperations`) to prove the real CREATE/DROP DATABASE mechanics work against a real throwaway database, cleaned up immediately after.
- **A one-time `tenants:backfill-databases` command** exists to migrate any tenant's data that predates this change out of the old shared database and into its new physical database, verified by row count on both sides before the operator clears the old copies.
